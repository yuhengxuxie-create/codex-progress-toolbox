# 后端升级与文件交付说明

本文件对应 v1.6.0，下载以该版本 GitHub Release 为准。完整安装包用于新安装；已有用户应使用专用 `upgrade-from-v1.x` 升级包，先校验再升级，不把新配置模板直接覆盖到旧目录。

## 旧版本与状态保留

- v1.5.0 完整生态后端使用 schema 10，v1.6.0 代码使用 schema 23。升级器须先停止旧服务并备份，再通过受控迁移入口更新数据库；只读 `status`、`validate` 不迁移数据库。已经使用 schema 23 的用户不因本轮文件校验修复再次提升 schema。
- 保留原配置、DPAPI 凭据、完整 `.state`（包括业务数据库、WAL、guardian 投递库、文件快照、审批观察状态）、绑定身份、关联密钥、监测名单和历史消息关联。未知发送结果必须保持未知，不能清空状态或重放历史文件来“修复”。
- 新增的本地失败恢复审计使用现有 `meta` 表，不增加数据库版本。仅当前运行队列中新发现、同轮同路径且从未提交的本地失败可重新校验并恢复。重启不会自动补发旧拒绝记录；已经保存的待发送快照继续按原幂等流程处理。
- 数据库位于升级器未保留的外部目录，或状态目录使用链接、重解析目录时，自动迁移应拒绝并明确说明原因，不能猜测复制目标。
- 回滚必须恢复同一次升级前的程序和数据库备份。旧程序不能直接降级读写新库。DPAPI 凭据也不能当作可跨电脑、跨 Windows 用户自由复制的配置。
- v1.2.0 Webhook 模板仅迁移严格验证的监测任务标识，不复用 Webhook、签名或旧凭据；该路线需要重新配置用户自己的飞书企业自建应用。不能把 v1.5.0 的验收结果推广成所有旧版本都已验证。

## 飞书权限与配置

审批提醒和本轮文件校验没有新增权限 scope。继续使用既有四项：`im:message:send_as_bot`、`im:message.p2p_msg:readonly`、`im:message:readonly`、`im:resource`。

从旧完整生态升级时，卡片操作需要长连接回调 `card.action.trigger`；底部菜单需要事件 `application.bot.menu_v6`，文字接收保留 `im.message.receive_v1`。这些配置及应用版本发布步骤见 [飞书升级权限说明](FEISHU_UPGRADE_PERMISSIONS.md)。不要因为使用卡片就新增 CardKit 权限，也不要要求已有用户重新绑定机器人。

## 文件未能交付时

系统会核对准确路径、普通文件类型、父路径安全性、大小和文件身份，再保存快照并交给通信守护发送。单个文件失败不阻塞同批其他文件，成功文件不因另一个文件被纠正而重发。

- “交付路径未找到”不能证明文件已被删除；可能是输出路径写错或文件尚未生成。让原任务返回实际生成步骤得到的完整路径。
- “无读取权限”或“文件已变化”需要处理对应的本机问题，再让原任务重新交付。系统不通过相似文件名、扩展名或最新修改时间猜文件。
- “发送结果未知”表示平台未给出可证明的结果；系统停止自动重发以避免重复。不要通过清空数据库或手工反复发送绕过去。
- 明确的暂时性平台拒绝由既有 guardian 使用同一幂等键退避重试；耗尽后保持明确失败，不另造一轮发送身份。

## 审批与预警的边界

审批提醒会复核当前轮次及待审批身份。没有可信远程审批句柄时，只提醒回到原审批界面，不提供虚假的一键批准。无法读取可信状态时不能保证还原已经消失的审批事件。

X 来源保留已完成的限流退避和部分覆盖说明。浏览器扩展、小时本机桥接、完整父关系及无人值守读取原型尚未完成验收，不作为本版本默认正式功能，不要求用户安装扩展或授予相关额外权限。

最新版通用文字说明及四页已批准图文指南随组件保留；本轮文件可靠性补充以本文为准，不把未经验证的新流程画入既有指南。
